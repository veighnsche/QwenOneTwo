# Prepared receiver component v1 — experimental admission and joint objectives

This RD-05 contract adds a named experimental component path. It is **not**
reference/receiver semantic qualification, model-execution authorization or a
native-writer semantic oracle. The [direct-state contract](direct-role-states-v1.md)
and unchanged bounds still admit zero existing receiver rows; that future-fit
blocker requires an explicit layout revision and coverage re-audit. No subset,
larger allowance, new annotations or threshold changes follow from this contract.

`frozen-w-pooled-role-slots-v1` and `direct-role-states-v1` use the existing
`ReceiverProducer`, `CleanEncoder`, `CleanPackets`, registry, runtime and Session.
The old D/pooled control remains distinct. Default reference qualification,
diagnostic-reference guards and native supervision masks are preserved.

## Binding and outcome boundary

`component_admission.admit_prepared_component` accepts only an original selected
receiver record from the pinned reviewed training release, its exact materialized
permitted view and independent clean encoding. Development/locked records, native
writer/reader/replay substitutes, altered views, extra attributes, foreign states
and ambiguous candidate identities reject. The actual current sealed request must
match the independently encoded ordered role payloads, rubric metadata, source
states/token/byte coordinates and complete evidence spans. There is no nearest-
vector, answer agreement, record-ID-only or prose keyword admission.

The resulting `PreparedReceiver` is bound to the exact Runtime instance, snapshot
Ref and complete content signature. It is mechanical provenance from the trusted
clean constructor, not a cryptographic proof or a semantic review of arbitrary
vectors. Labels attach only after the actual complete request forward, with a
second content/binding validation. Reviewed selection and Boolean feasibility
targets map to stable Refs in that actual bank. Generic unknown feasibility stays
unlabeled; no fourth-class label is invented.

No outcome, Reason, desired value or selected winner enters request features,
source caches, field lengths, routing or admission. Record hashes bind reviewed
identity outside model inputs. The receipt states `experimental: true`,
`reference_qualification: null`, `receiver_behavior_accepted: false`.
`collect_session` requires this actual receipt for new-profile optimization and
rechecks its binding; it still rejects diagnostic-reference episodes first.
Unsupported writer-generated semantics keep their masks. RD-06 owns any later
native admission extension.

## Objectives, masks and owners

Use existing `decision_losses`, `Eligibility`, within-example normalization and
`Window` eligible-example means. `Eligibility` is factored unchanged into a
model-free module and re-exported from `losses`. The coefficients remain status1,
Noul1, Choice1, Score1, feasibility0.5, alignment1 and structure0.5. There is no
auxiliary count objective or development-dependent coefficient/sampling change.

Supported status loss is independent of predicted status. Reviewed Assessed
Noul/Choice/Score targets remain eligible even when the model abstains. Feasibility
uses only explicitly reviewed candidate labels. Reason requires a supported
post-forward target and matching actual/reference non-assessed status.

**New-profile Reason targets are unsupported and masked.** No reference Reason
encoding is invoked for these profiles, and an attempted target injection rejects.
There is no zero-filled explanation or structure target counted as eligible.
The old profile's explicit post-forward Reason/isolated-reader exception remains
unchanged: outcome-bearing approved Reasons are permitted only on those supported
branches and never as request content. New-profile reader support is not claimed.

W, R, the startup row and the immutable reference remain frozen. D, selected
existing receiver owners and the direct profile's live residual projection are
declared by exact names/shapes/dtypes in preparation and actual Window ownership.
The writer-only role-length head stays frozen during receiver work. One named
owner per parameter and the original clipping/Adam/window/checkpoint algorithms
remain authoritative.

For direct construction, restore the exact existing parent Window first, then
`extend_profile_window` adds zero-delta projection owners. Existing masters, Adam
moments, schedule/update counters and RNG are retained; new projection moments
remain absent until a real eligible gradient. This construction does not step an
optimizer or authorize a fit. Subsequent resume uses the existing transactional
checkpoint implementation with the new complete owner/profile identities.

## Measurements and pending qualification

`summarize_joint_learning` retains full ordered panels and separates head status/
value evidence from actual decoded/delivered success. Per-operation raw readouts,
status confusion, per-operation/reference-status cells, eligible-example counts
and explicit Reason masks prevent correct abstentions from hiding assessed Noul
failure or Score status collapse. It reuses the original graders and intervals.

Startup retention compares paired raw scalars and mapped budgets under identical
record/input identities. It checks the existing ordered FP64 continuous mapping
and discloses overrides separately. A frozen private startup row does not protect
shared D features from drift. Missing startup data stays unmeasured. Head-only
components never claim delivery, native invocation or accepted learned behavior.

`RD05-GPU-GRADIENT-ACCUMULATION` and `RD05-GPU-RESUME` are implemented in
`tests/test_joint_receiver_gpu.py`, **pending RD-07, never executed in RD-05**.
They require submitted RD-07, `QOT_RD05_GPU_QUALIFY=1`, the pinned snapshot and
exact 3090 UUID before model imports. The first uses an existing reviewed
frozen-W/pooled component and actual Window VJPs without an optimizer step. The
second checks parent-to-direct owner/moment/RNG preservation and transactional
complete-window save/resume with declared engineering perturbations and no update.
Direct corpus admission remains unsupported; RD-04 owns its separate projection
engineering gradient assertion. No CPU/3060 model fallback is permitted.

All six RD-03/RD-04 GPU checks remain pending as well. RD-07 must resolve every
required check before a separately authorized fit. This contract certifies no
learning outcome, Reason meaning, semantic accuracy or production readiness.
