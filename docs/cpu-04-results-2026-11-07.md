# CPU-04: bounded recurrence retention — 2026-11-07

A 32-entry cache improves the existing read-only diagnostic pack on both GPUs.
All three same-card pairs reduce CPU work and elapsed case time. The option is
available as `prepare --cache-limit 32`; ordinary model/training defaults remain
eight. No model arithmetic, weights, training data, agents or services changed.

## Method and acceptance

The [retention contract](recurrence-cache-retention-v1.md) defines the exact
finite work. The existing worker/dispatcher loads once per card, prewarms only
immutable reference payloads, then runs capacities **8,32 / 32,8 / 8,32**. Each
trial clears recurrence workspace and runs a complete cold warmup before a timed
pack. Timed packs have **both detailed profiling and counters off**. Separate
untimed observations count warm cache behavior. D source states and Sessions
stay fresh. No wall-clock cutoff or retry loop is introduced.

There are **123 actual presentations per card / 246 total**, including shared
startup, reference prewarm, warmups, timed work and counter observations. Total
objective-ledger positions for these resident comparisons are **33,148**; offline encodings/capture work are
separate computation, not invented Session positions. No optimizer is constructed
or stepped. No capability training, new semantic data/reviews or agent work.

## Correctness and scope

The parent and independent audit compare **every repeated case receipt exactly**
against the first case on that card: outputs, tensor audit hashes, provenance,
bindings, grades, complete ledger/control/cache receipts and single prefill/lineage.
All 246 presentations pass their applicable checks; unique startup anchors have
separate transport/admission validation. W’s 320 tensors/tying and receiver/reference identity
checks pass before/after with frozen parameters and grad=None. The data release
and final checkpoint 188 are unchanged. Existing semantic failures remain.

The existing recurrence suite passes **8/8 on each GPU at capacity 32**, against
the retained eager oracle: exact outputs/first derivatives, 512/1024 connected
cache compositions, checkpoint repeats, FP64 directional checks, eviction/stream
isolation and failure guards. CPU schema/dispatch/device tests pass **25/25 in
8.698 s**; a final explicit-execution guard test passes separately. The original
numeric matrix is reused. Recurrence, Session, neural guards, backbone and actual
case evaluator are byte-identical to CPU-03 commit `4879331`.

The plan pins capacity and all sources/data/weights. Worker job admission checks
the complete scheduled descriptor. The benchmark is a specialization of the
existing dispatcher/worker, not another service or agent coordinator. All cold
costs and partial receipts are retained; failed runs cannot silently replay.

## Normal-runner integration

The normal runner now reports parent **main-phase wall time**, from readiness
admission through the last validated main result, separately from setup/final
integrity. A single finite first-pack comparison through the normal runner passes, with
case receipts exactly matching the respective card’s resident benchmark:

| 32-entry run | Main phase | Main cases/s | End-to-end | Worker CPU seconds/case |
|---|---:|---:|---:|---:|
| 3090 alone | 11.418856 s | 0.700596 | 37.941083 s | 1.416431 |
| Both cards | 7.132641 s | 1.121604 | 34.982324 s | 1.511074 |

Main-phase throughput improves **1.600930×**; end-to-end improves **1.084579×**
because startup dominates this small pack. Both cards use **6.6818% more worker
CPU per case**, and **65.8653% more setup-inclusive CPU per main case**
(4.576487 → 7.590806 CPU seconds/case). Parallelism uses available CPU cores;
it is a different tradeoff from the cache policy’s same-card CPU reduction.
The 3090 handles three cases, the 3060 five; pairs remain intact.

Peak main allocation is 1,999,106,560 bytes for 3090 alone. In the two-card run
it is 1,991,500,288 / 1,978,402,304 bytes (3090/3060). These runs add **25 actual
presentations** including startup; total CPU-04 evidence contains **271**.
The independent integration audit passes, with unchanged weights, zero updates
and exact same-card receipts. This is not a stable long-run scaling or full
310-case throughput claim. End-to-end includes metadata preparation and final
integrity; the main-phase timer includes dispatch and result validation.

## Decision and next slice

Use the explicitly selected 32-entry option for this read-only diagnostic pack.
Keep the ordinary model/training policy at eight: this work does not qualify
training memory or authorize further training. Do not add these savings to prior
finite-check percentages or claim learned invocation/native answer competence.

The next performance target is CPU-06: use the existing trace to choose a larger
pure backbone region between the mandatory guards, with a separate execution
specification and measured benefit. Audit transfers are not the next demonstrated
bottleneck here. No finite check is removed/deferred and no larger capture is
implemented by CPU-04.
