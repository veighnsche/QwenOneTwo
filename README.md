# QwenOneTwo

[GitHub repository](https://github.com/veighnsche/QwenOneTwo) ·
[Documentation map](docs/README.md) ·
[Repository and artifact guide](docs/repository-and-artifacts.md)

One Qwen3.5-0.8B backbone, Qev's separately switchable decision LoRA, and GPU-trained internal controls. Submit one prompt: Qev is enabled for a continuous thinking-budget score, native Qwen generates, and a learned hidden-state gate can temporarily enable Qev for Noul, Choice or Score. The result returns through a learned hidden feedback vector; Choice includes the selected candidate and its position. The normal answer remains generated by Qwen. Generation continues into the normal answer.

There is one prompt prefill and one hybrid cache. Internal calls use latent vectors, not generated tool JSON, a separate HTTP decision request, or another button press. Four **routing operations** are distinct from the continuous thinking-budget **regression**. Choice/Noul use Qev's pretrained pointer; Score and the initial budget use separate scalar regression rows. The budget row and a separate generic Score row are installed in Qwen's actual tied vocabulary output matrix, outside the tokenizer vocabulary, and are masked from generated text.

## Prototype status and limits

**The complete learned decision flow is not ready or implemented.** The [architecture and training plan](docs/architecture-and-training-plan.md) describes proposed question formation, candidate/rubric memory and native result interpretation. Representation, state/gradient strategy and an initial data/readiness plan are recorded; annotation review and broader GPU qualification remain incomplete. The bounded G1-core proof is now measured separately. The prototype and setup commands below do not implement that plan.

The existing implementation is a trained research prototype. It has a small, reproducible synthetic curriculum: native answers, application-status Noul decisions, two-option color choices, completion scores, and manually specified effort preferences. New behavior consists of a rank-4 native routing LoRA, learned internal gate, candidate-boundary selector, latent query/feedback bridges, and a scalar output row. The pretrained Qev LoRA and pointer remain frozen. No external model or keyword/regex semantic router is used in production. The runtime never imports curriculum generation rules.

The initial score is an illustrative effort preference, not a proven optimal budget. Broad decision quality, general invocation ability, and answer improvement have not been established. Candidate selection is learned and may fail; missing candidates are recorded rather than fabricated. At most 16 internal requests are allowed per run, and at most one is processed per generated-token boundary.

**Cache compatibility remains experimental.** Qev's published runtime independently encodes explicit decision questions. This project newly trains latent invocation while sharing Qwen's attention/recurrent cache across adapter modes. Cache identity and single-prefill counts are checked, but that does not establish equivalence to an entirely base-mode or adapted-mode history. The published Qev checkpoint used short decision contexts; no long-context latent performance is claimed.

In the existing prototype, thinking and answering have separate limits. The maximum thinking budget is half the pinned 262,144-token context: 131,072 tokens. For scalar `s = clamp(raw, 0, 1)`, the budget is `floor((3*s*s - 2*s*s*s) * 131072 + 0.5)`. The S curve is retained. Natural early closure, zero-budget closure, cancellation and a manual override are supported. Internal latent steps are counted separately from thinking/answer text tokens. The frontend shows adapter activity and each real decision event.

## GPU-only setup

All inference, training, extraction, fitting and real-model tests require CUDA. There is no CPU fallback. The configured GPU is the RTX 3090, UUID `GPU-225509c3-d702-6c27-de03-76b5e99b33b1`. Ordinary editing, static validation and browser tests may use CPU.

```sh
uv sync
export CUDA_VISIBLE_DEVICES=GPU-225509c3-d702-6c27-de03-76b5e99b33b1
export QOT_DEVICE=cuda:0
export QOT_HF_CACHE=/path/to/huggingface/cache
uv run python -m qwen_one_two.download --data data
uv run python -m qwen_one_two.train --cache "$QOT_HF_CACHE" --router-steps 240 --latent-steps 800 --head-steps 600
uv run python -m qwen_one_two.refine_routes --cache "$QOT_HF_CACHE"
ln -s one-two-v1-routes-2 data/trained/current
uv run python -m qwen_one_two.train_feedback --cache "$QOT_HF_CACHE" --steps 420
ln -sfn one-two-v1-feedback-3 data/trained/current
uv run python -m qwen_one_two.train_feedback --cache "$QOT_HF_CACHE" --output one-two-v1-feedback-6 --steps 120 --only-operation choice --choice-index-only --first-answer-weight 4
ln -sfn one-two-v1-feedback-6 data/trained/current
uv run qwen-one-two
```

Training saves `data/trained/one-two-v1/`: routing adapter, controls, exact curriculum, hashes, device, losses and steps. Both-phase routing is trained in `one-two-v1-routes-2`; full-answer feedback and explicit Choice-position feedback are trained in separate checkpoints. The active artifact is `one-two-v1-feedback-6`; the `current` symlink selects the active artifact. A complete checkpoint is never silently overwritten. Loading validates its base revision, Qev revision and artifact hashes. The browser's verify button validates trained artifacts; it does not start training or fit a substitute demo head.

The official Qwen revision is `2fc06364715b967f1860aea9cf38778875588b17`. Qev is pinned to `twainsk/qev-0.8b` revision `1d2a6d7f891daab7483a49c3abe507c0c9d7ea62`. The download command retrieves weights as data and verifies the upstream release manifest; it never runs upstream code. The Python runtime uses Qwen's text language model; visual inputs are not exposed by this UI.

## Verification and deployment

```sh
uv run python -m unittest discover -s tests -p 'test_*.py'
# Real model: explicitly selected RTX 3090 only.
uv run python tests/smoke_gpu.py --cache "$QOT_HF_CACHE"
```

The GPU demonstration checks verified native translation, internal Noul → “Yes”, Choice → “B: blue”, and Score → “0.7”, with one prefill and an identical cache in each run. These are bounded functional demonstrations, not a general quality benchmark. Separate answer-phase probes use explicitly identified teacher-forced prefixes. The real-model check observes backbone forwards to verify one prefill, single-step continuations on the identical cache, CUDA placement, adapter transitions, scalar readout, actual learned gate requests and a normal answer. Bounded generation uses explicit test overrides. It also checks cancellation and rejects missing/tampered training artifacts. Reports live in ignored `artifacts/`.

A loopback HTTP server listens on port 3211. Exact Host/Origin checks, no cross-origin API access, single model-operation ownership and targeted cancellation remain in place. Configure `QOT_PUBLIC_ORIGIN` for HTTPS reverse proxying. The application is independent of The Operating Table. Deployment templates are in `deploy/`; the renamed mount is `/qwen-one-two/`, with old `/qwen-budget/` links redirected when deployed.
